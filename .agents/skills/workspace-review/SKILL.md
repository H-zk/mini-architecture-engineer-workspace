# workspace-review

> 本工作区仓库未提交变更的「评审 → 反馈 → 修复 → 主题化提交」操作流。评审对象 = 工作区仓库自身（规则文档、任务产物、知识库、工具脚本）；**不含** `src/` 业务代码评审（那是 feat-plan-research 等执行流的审核子协议）与工作流机制审计（workspace-grill）。

## When（何时触发）

- 操作者说「review 一下暂存区/工作区的改动」「这批改动怎么样，给我反馈」「好的改动/不好的改动/还有什么建议」。
- 反馈确认后操作者说「处理遗留问题」「按你的反馈/建议修」。
- 操作者说「拆成 N 个 commit」「按主题分别提交」「每次只提交对应的内容」（通常紧接 review 之后，也可独立触发）。

## Why

大批量未提交改动常混合多条主线（机制落地 + 任务快照 + 知识沉淀），一并提交则历史难追溯；评审若只读 diff 不实测，结论本身可能是错的——实证：链接只验目标存在、没 resolve 相对层级时，真断链被误判为「门禁误报」；大批次单会话通读仍漏检多项，分主题独立深评才纠回。所以评审结论要过证据门槛、修复要过既有裁决核对、拆分要 hunk 级操作——三者都是本 skill 的核心价值。

## Steps（操作流）

0. **状态核实（先于一切结论）**：`git status --porcelain=v1` + `git diff --stat`（unstaged）+ `git diff --cached --stat`（staged）。操作者说「暂存区」时常泛指全部未提交改动——**暂存区为空 ≠ 无改动**，以实际状态为准，报告开头说明口径（staged / unstaged / untracked 各多少）。

1. **读全 diff，三类都覆盖**：modified 分块读（输出过大先落盘再分块读）；untracked 新文件逐一读（最易漏——`??` 清单就是待读清单）；删除与 rename 也要看（rename 相似度旁仍可能有实际内容改动）。

2. **意图归纳 + 主线分组**：提炼 2–4 条改动主线（每条 = 意图一句话 + 对应文件清单）；**跨主线混合文件单独列表**——这是后续拆 commit 的关键输入。

   - **大批次分主题并行深评**（≥40 文件或 ≥3 条主线时建议启用；操作者明示「分多主题、独立 review」必启用）：按主线委派独立 subAgent **只读**深评（subAgent 通用协议见 [WORKFLOW §2.6](../../../WORKFLOW.md)——prompt 自包含锚指针、独立回流、主会话只传话不执行）；本 skill 特化三点——subAgent 间互不读对方产物与主会话初步结论（防锚定）、主会话拆分的文件清单精确到混合文件的行归属、交叉对照合并时逐条标注发现方（subAgent 纠正主会话误报须透明化：谁纠正、依据什么）。

3. **结构化反馈（三段式，先交操作者，未确认不动手）**：

   - **变动意图总览**：主线 + 各自规模。
   - **好的改动**：相对原状态的实质改进，讲清为什么好（不止「改对了」）。
   - **问题与建议（P0/P1/P2 统一排序）**：问题（已发生的缺陷）与改进建议合入单列表按优先级排序；每条**负向结论**（问题/瑕疵，无论 P0/P1）带实锤证据（`文件:行号` / grep / 实测输出），建议类不强制：
     - **P0 须修**：错误级问题（事实错误 / 自相矛盾 / 断链 / 脚本 bug）与低成本一致性修复，不修不提交；
     - **P1 应修**：瑕疵级小问题（不影响正确性）与改进项——与 P0 只差严重度、不差处置要求，**处理完才能提交**；确需延后的经操作者明示处置（豁免 / 登 BACKLOG / 注明触发信号下批修），AI 不得自行延后；
     - **P2 操作者定**：基准、裁决、命名类——只提示不代决，不阻塞提交（除非操作者裁决处理）。

4. **结论交叉验证（review 自身要过证据门槛）**：下负向结论（问题/瑕疵）前实测——grep 过期引用与断链、跑 `python .tools/workspace-check.py`、wc/find 量测、抽查新文件内容。专项手法：
   - **链接类结论（无论断链还是排除断链）必须从链接出发点 resolve 相对层级再验证**——目标文件存在 ≠ 链接正确（`../../` 差一级时同名目标常仍存在，真断链会被误判成「门禁误报」）。
   - 涉个人数据/身份信息机制的批次加**敏感实体首现扫描**：staged diff 中 grep 公司名/身份明细，对照 `git grep <词> HEAD` 判定是否首次进入 committed 层——首次进入须显式提示操作者。
   - **表格增补类 diff 对账既有行未消失**（HEAD 行数 + 新增 = 终态行数）——新增行写成「替换」而非「上方插入」会静默删掉既有行，逐行读 diff 极难察觉。
   - **动手修复前先重核工作区既有约定与先例**（grep 相邻规则、历史裁决）：review 结论与明示约定冲突 → 约定优先，撤销误报并向操作者透明说明。

5. **修复执行（操作者确认反馈后）**：逐条处理授权项；修复保持 **unstaged** 与原批次区分（暂存区边界默认，见 AGENTS「安全红线 · 暂存区边界」）；改带 frontmatter 的文档同步 bump `updated-at`。**波次编排**：同文件多处改动分波推进，波内文件集不相交才可并行（防编辑撕裂）；`updated-at` bump 收拢为独立一波；P0/P1 与 P2 分轮、逐轮授权。修复后复跑 workspace-check（涉真源跑全量）——`--staged` 聚焦检查读的是工作树内容，unstaged 修复同样被看到，可直接用它验证修复效果。**大批次（≥40 文件或 ≥3 主线）修复轮收尾后加一轮终审复核**（独立只读 subAgent 或主会话冷启动）：修复轮自身会引入新问题、原批次也可能有历轮漏检项。

6. **主题化提交（操作者明确授权 git add / reset / commit 后）**：

   - 按主线分组文件；提交信息遵循仓库惯例（前缀与格式**现查 `git log` 近期条目**为准——惯例会变，不写死）。
   - **混合文件 hunk 级拆分两法**：
     - **补丁法**：`git diff HEAD -- <file>` 按 hunk 切分 → `git add <file>` 后 `git apply --cached --reverse <摘除补丁>`，把不属于本 commit 的 hunk 从索引摘除；
     - **临时编辑法**（相邻改动被 git 合并成单 hunk、补丁法切不开时）：`cp` 备份文件 → 编辑到中间态（只留本主题改动）→ add / commit → `cp` 备份精确还原。**中断恢复**：会话在 commit 后、还原前中断时工作区会停在中间态——接手先 `git status` 对照备份把文件还原到最终态再继续，勿在中间态上续作。
   - **每个 commit 前逐文件核验**：`git diff --cached --stat` + 关键文件 `git diff --cached <file>`，确认暂存集只含本主题内容。
   - **commit 前机器门禁（lint-staged 式，聚焦暂存集）**：暂存集就绪后跑 `python .tools/workspace-check.py --staged`——只检查暂存文件（markdownlint / 任务 schema+产物 / 链接 / 密钥扫描按文件聚焦；archive 任务只查 schema 与必达已完成，与全量同口径），`errors=0` 才 commit；全局分区（worktrees/temp 等）不在此跑，任务收尾仍按收尾门禁（`--task` / 全量）。
   - **commit 信息确认门禁**：机器门禁过后、执行 commit 前，把**完整提交信息（标题 + 正文）展示在会话内**，操作者确认后才执行 commit——未展示或未确认不提交；多 commit 拆分时每个 commit 的信息逐一展示确认。
   - **完整性验证**：Σ各 commit 增删行数 == 净 diff（`git diff <拆分前基线> HEAD --stat`），且 `git status` 干净——证明拆分无丢失、无重复。
   - 默认不 push（授权另说）；temp 拆分产物（补丁、备份）用完即清。

## Gates（门禁）

**交付反馈 / 执行提交前，以下全「是」才继续**：

- [ ] 状态口径已说清（staged / unstaged / untracked）？untracked 新文件、删除、rename 都已覆盖？
- [ ] 大批次（≥40 文件或 ≥3 主线）已按判据评估分主题并行深评？混合文件的行归属已划清？
- [ ] 每条负向结论（P0/P1 问题）有实锤证据（路径/行号/实测输出），无凭印象的结论？
- [ ] 修复动手前重核过既有约定/先例？误报已撤销并透明说明？
- [ ] 问题与建议已合入单列表按 P0/P1/P2 排序，未把裁决类（P2）当问题？
- [ ] **P0 与 P1 已全部处理**（修复，或经操作者明示处置）？——全处理才进提交流；P2 未擅自代决？
- [ ] git 写操作（add / reset / commit）均在操作者明确授权后执行？修复轮保持 unstaged 与原批次区分？
- [ ] 每个 commit 暂存集已逐文件核验只含本主题内容（含混合文件的 hunk 摘除核验）？且 commit 前已跑 `--staged` 聚焦检查 `errors=0`？
- [ ] commit 信息已在会话内展示并经操作者确认（多 commit 逐一确认）？
- [ ] 完整性验证通过（Σ行数 == 净 diff、status 干净）？未 push？

> 反例信号：反馈被纠「漏了新文件 / 结论凭印象 / 修了不该修的（撞既有约定）/ 链接只验目标存在没 resolve 层级 / 大批次没拆主题致漏检 / 修复轮漏 bump updated-at / commit 混了别的主题」，几乎都是上面某条没过。

## Outputs

- **评审报告**（对话输出，三段式：总览 / 好的改动 / 问题与建议 P0-P2 统一排序）——评审本身不立项、不写 exps；引出的机制类候选走 `BACKLOG.md` 指针（唯一真源）。
- **修复轮**（unstaged，与原批次可区分）。
- **N 个主题 commit**（信息含正文明细；默认不 push）。
