# 文档编写规范

## 文件读写编码

所有知识库文档为**无 BOM 的 UTF-8** 编码。修改文档时必须通过 Node.js（`fs.readFileSync`/`fs.writeFileSync` + `'utf8'`）操作，禁止使用 PowerShell 5.1 的 `Get-Content`/`Set-Content`（会破坏编码）。详见 `SKILL.md` 的 `## 平台注意事项`。

## 路径与引用

- 引用源文件使用**从项目根目录出发的相对路径**（如 `{模块}/src/{文件}` 或 `{模块}/{子目录}/{文件}`）
- 在 monorepo 项目中，路径必须包含子项目前缀，不要省略为 `src/...`
- 引用具体代码位置使用 `文件路径:行号` 格式
- 基于实际代码分析编写，不凭猜测

## 交叉引用原则

同一知识点只在一篇主文档中完整描述。其他文档需要涉及该知识点时，使用交叉引用：

```markdown
详见 `notes/{编号}-{名称}.md` 的 `{章节标题}` 章节
```

判断哪个文档应包含完整描述的规则：
1. 按业务域归属：知识点属于哪个业务域就写在对应的文档中
2. 按文件归属：知识点主要涉及的源码文件属于哪个文档的"关键文件"范围
3. 按首次出现：如果前两条规则无法判断，以 `/knowledge-create` 时首次完整描述的文档为准

### 交叉引用写入时机

以下操作**必须**检查并消除内容重复：

- `/knowledge-create`：创建新文档时，扫描已有文档，如发现与新文档内容重叠的知识点，在新文档中使用交叉引用替代完整描述
- `/knowledge-merge-temp`：合并时如新增的知识点在目标文档外的其他文档中已有描述，改为交叉引用
- `/knowledge-improve`：更新文档后，检查更新内容是否与关联文档重复

### 常见的重复场景及处理原则

当两个文档对同一知识点都有描述时，按以下原则决定保留位置：

1. **数据模型** → 在"模型所属业务域"的文档中保留完整字段表，另一文档用交叉引用
2. **配置项** → 在"配置/部署"相关文档中保留完整版，业务模块文档引用
3. **异步任务** → 在"任务所属模块"文档中保留完整版，跨模块总览文档引用
4. **权限/认证机制** → 在"权限系统"相关文档中保留完整版，其他文档引用

## 业务流程写作

每个业务流程必须包含：
1. **触发条件**：什么情况下触发该流程
2. **核心步骤**：流程的主要操作步骤（使用代码块展示调用链）
3. **结果状态**：流程完成后的状态变化

## Mermaid 图示使用规范

### 何时使用图示

以下情况**应该**使用 mermaid 图示：
- 模块有 3 个以上参与组件的交互流程（用 `sequenceDiagram` 或 `flowchart`）
- 有明确状态流转的数据模型（用 `stateDiagram-v2`）
- 有继承/组合关系的核心类（用 `classDiagram`）
- 有分层或多系统交互的架构（用 `graph`）

以下情况**不需要**图示：
- 简单的 CRUD 操作
- 线性的单步骤流程
- 已能用表格清晰表达的内容

### 图类型选择指南

| 场景 | 推荐图类型 | 说明 |
|------|-----------|------|
| 分层/系统架构 | `graph TB`（自顶向下） | 用 subgraph 分组，展示层间依赖 |
| 类继承/组合 | `classDiagram` | 展示属性和方法签名 |
| 时序交互 | `sequenceDiagram` | 展示组件间的调用顺序和参数 |
| 条件分支流程 | `flowchart TD` | 支持菱形判断和分支标签 |
| 状态机 | `stateDiagram-v2` | 展示状态值、转换条件和阶段 |

### 图示写作要求

- 每个图应配有**文字说明**（图前或图后 2-3 句话描述关键信息）
- 节点标签使用**可读描述 + 标识符**的组合（如 `"方法名()<br/>功能描述"`）
- 单个 mermaid 图不超过 30 个节点，超过则应拆分为多个图
- 复杂模块可有多张图（架构图 + 时序图 + 状态机图），但每类图不超过 2 张

## 变更历史

每个主文档的 `## 变更历史` 章节记录文档的**结构性变更**，而非所有修改。

### 记录门槛

只有以下类型的变更才写入变更历史：
- 新增或删除整个章节
- 文档拆分或合并（由 `/knowledge-refactor` 触发）
- 业务域重新划分（如某功能的归属从 A 文档移至 B 文档）
- 数据模型发生重大变化（新增/删除核心实体）

以下变更**不记录**到变更历史：
- 内容微调、措辞优化、行号修复
- 补充或更新已有章节内的细节描述
- 移除过时的小段内容

### 条数限制

- 每个文档的变更历史**最多保留 5 条**
- 追加新记录时，如果已超过 5 条，自动裁剪最旧的记录
- 格式：`| {YYYY-MM-DD} | {变更摘要} |`

### 写入时机

- `/knowledge-create` 创建时写入初始记录（1 条）
- `/knowledge-merge-temp` 合并时，仅在产生了结构性变更时追加
- `/knowledge-improve` 更新时，仅在产生了结构性变更时追加
- `/knowledge-refactor` 重构时必定追加

## 文件命名

- 主文档：`{两位编号}-{kebab-case 名称}.md`（如 `01-{模块名}.md`）
- temp 文件：`{两位序号}-{kebab-case 描述}.md`
- temp 文件必须包含 `## 关联主文档` 字段
