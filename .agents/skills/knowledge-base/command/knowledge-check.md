# /knowledge-check

对知识库进行全面健康检查，判断文档是否与代码保持同步、结构是否合理，并给出改进建议。

## 参数

- `$ARGUMENTS`（可选）：
  - 不传：检查所有主文档
  - 指定编号或文件名（如 `05`）：只检查指定文档
  - `--auto`：静默模式，只输出问题列表，不交互

## 检查周期

- 至少每 **30 天** 执行一次全量检查
- 判断依据：文档末尾元数据中的 `last-checked` 日期距今是否超过 30 天
- 如果超过 30 天未检查，Agent 应在适当时机提醒用户执行 `/knowledge-check`

## 执行步骤

### 1. 读取知识库配置

从 `AGENTS.md` 的 `## 知识库 → ### 目录结构` 解析主文档列表。

### 1.5 可选：运行确定性校验脚本

如果环境中可用 Node.js，优先运行校验脚本获取基础数据：

```bash
node .agents/skills/knowledge-base/scripts/validate-knowledge.js
```

脚本输出 JSON 格式的校验结果，包含：
- 所有文档中引用的文件路径及其存在性
- temp 目录的文件数量和最旧文件日期
- 每个文档的 last-checked / last-updated 日期

Agent 基于脚本结果进行语义层面的分析（代码覆盖率、结构健康度等）。
如果脚本不可用，继续执行手动检查流程。

### 2. 逐文档检查

对每个主文档执行以下检查项：

#### 2a. 时效性检查

1. 读取文档末尾的元数据块（`last-checked`、`last-updated`）
2. 计算距今天数
3. 如果 `last-checked` 超过 30 天 → 标记为 **需要检查**
4. 如果 `last-updated` 超过 60 天 → 标记为 **可能过时**

#### 2b. 引用完整性检查

1. 提取文档中所有引用的源码文件路径（`{模块}/{目录}/{文件}` 格式）
2. 检查每个文件是否存在
3. 对于包含行号的引用（如 `src/xxx.js:42`）：
   - 读取文件对应行附近的内容
   - 做模糊匹配（检查该行附近是否包含文档中提到的函数名/变量名）
   - 不要求精确行号匹配（代码编辑会导致行号自然偏移）
   - 如果目标函数/变量在文件中完全不存在 → 标记为 **引用失效**
   - 如果目标函数/变量存在但行号偏移 → 标记为 **行号偏移**（仅提示，非错误）

#### 2c. 代码覆盖率检查

对文档覆盖的业务域：

1. 扫描相关源码目录（路由、数据层、视图、API）
2. 对比文档中描述的功能与代码中实际存在的功能
3. 代码中有但文档未提及的功能 → 标记为 **覆盖缺失**
4. 文档中有但代码中已不存在的功能 → 标记为 **内容过时**

#### 2d. 结构健康度检查

1. 文档长度：超过 300 行 → 标记为 **过长，考虑拆分**
2. 章节深度：嵌套超过 4 级 → 标记为 **结构过深**
3. 内容密度：大段文字没有代码引用 → 标记为 **缺少代码依据**
4. 重复度：检查是否有多个文档描述同一文件/功能 → 标记为 **职责重叠**

#### 2e. temp 积压检查

1. 统计 `notes/temp/` 下的文件数量
2. 检查每个 temp 文件的创建/修改时间
3. 文件数量 ≥5 → 标记为 **积压，建议合并**
4. 最旧的 temp 文件超过 14 天 → 标记为 **高风险积压**
5. 最旧的 temp 文件超过 30 天 → 标记为 **严重积压，优先处理**

#### 2f. skill 局限性检测

基于检查结果识别反复出现的问题模式，判断 skill 自身是否需要改进：

1. **反复过时**：同一文档连续 2 次 `/knowledge-check` 被标记为需要更新 → 建议执行 `/knowledge-evolve` 评估文档粒度
2. **反复引用失效**：多个文档出现同类引用失效模式（如行号大面积偏移） → 建议执行 `/knowledge-evolve` 优化引用规范
3. **模板不匹配**：文档中出现模板未覆盖的章节结构 → 建议执行 `/knowledge-evolve` 更新模板
4. **temp 积压反复**：temp 文件频繁超过 5 个 → 建议执行 `/knowledge-evolve` 调整合并触发策略

### 3. 汇总结果

#### 3a. 生成检查报告

```
知识库健康检查报告（2026-05-22）

📊 总览：
  主文档：12 个
  需要更新：3 个
  需要重构：0 个
  健康：9 个

📝 需要更新的文档：
  05-user-management.md
    ⚠️ 覆盖缺失：新增批量导出接口（3 个接口未记录）
    ⚠️ 行号偏移：app/services/user.py 引用偏移 5 处
    ⚠️ 可能过时：last-updated 距今 45 天
    → 建议执行：/knowledge-improve 05

  09-navigation-and-routing.md
    ❌ 引用失效：app/routes/home.py 不存在（已删除）
    ⚠️ 覆盖缺失：新增 /exports 路由模块未记录
    → 建议执行：/knowledge-improve 09

  🔧 需要重构的文档：
  （无）

📁 temp 增量笔记：
  文件数：{N}
  最旧文件：{日期}
  {状态：✅ 无积压 / ⚠️ 建议合并 / ❌ 严重积压}
```

#### 3b. 判断是否需要重构

当出现以下情况时，建议执行 `/knowledge-refactor`：
- 有 **2 个以上** 文档标记为 **过长** 或 **职责重叠**
- 存在明显需要拆分或合并的文档对
- 整体结构无法反映当前业务模块划分

如果需要重构：
- 生成重构计划文件：`temp/knowledge-refactor-{日期}.md`
- 在报告中输出计划路径
- 后续由用户执行 `/knowledge-refactor --from-plan {计划路径}`

#### 3c. 全部通过

如果所有文档都健康：
- 更新每个文档的 `last-checked` 元数据为当天日期
- 输出简短的健康报告

### 4. 更新元数据

- 对所有已检查的文档，更新 `last-checked` 为当天日期
- 未更新的文档（需要 improve 或 refactor 的）也更新 `last-checked`，但保留原有 `last-updated`

### 5. 输出建议操作

根据检查结果，输出可执行的命令列表：

```
建议操作：
  /knowledge-improve 05       # 更新 user-management 文档
  /knowledge-improve 09       # 更新 navigation-and-routing 文档
  /knowledge-improve          # 或一次性更新所有需要更新的文档
```

## 退出码与判断

| 情况 | 输出 |
|------|------|
| 全部健康 | ✅ 知识库状态良好，已更新检查日期 |
| 有文档需要更新 | ⚠️ N 个文档需要更新，建议执行 /knowledge-improve |
| 有文档需要重构 | 🔧 知识库结构需要重构，计划已生成：{路径} |
| 有 temp 积压 | 📁 temp 文件积压（N 个），建议执行 /knowledge-merge-temp |
| 检测到 skill 局限性 | 🔄 发现反复出现的问题模式，建议执行 /knowledge-evolve |

## 示例

```
/knowledge-check              # 检查所有文档，输出完整报告
/knowledge-check 05           # 只检查 05-user-management.md
/knowledge-check --auto       # 静默模式，只输出问题列表
```
