# series-phase-task-manage｜大任务系列容器模式（总目录 + 子阶段目录）

> 定位：回答「大需求**怎么切着交付**」。「怎么干快」是执行手段（任务内 subAgent 分治），与本模式分层不互斥——先判交付结构，再在阶段内部选执行手段。适用判别、拆分建议由 AI 提议、操作者裁决：本 skill 提供形态与检查面，不做门禁。

## 一、适用判别（先判「要不要用本 skill」）

| 问 | 走系列容器 | 走一个任务 + 多 subAgent |
| -- | ---------- | ----------------------- |
| 产物形态 | 要分批交付（阶段 = 带出口的交付单元：有确认点 / 提测 / 发布语义） | 一次性收敛（并行取数 / 分析 / 评审，产物一批齐） |
| 时间跨度 | 跨迭代窗口（需要阶段级迭代归属记录） | 单窗口可完成 |
| 管控需求 | 需总体把控四账（范围 / 分期 / 外部单据 / 遗留） | 单 plan 子任务表够管 |

两者不互斥：系列的一个阶段内部可以再用 subAgent 分治。判别结论与理由随任务立项 / plan 一句话留痕（如「组织判定：系列容器（命中：阶段交付 + 跨迭代）」）。

## 二、结构约定

**系列总目录 = 需求身份 + 总体把控**（仍是标准任务目录，README + CURRENT 锚点照常、机检不变）：

- README：需求全景 + **系列地图**（分期清单 + 各阶段目录指针 + 遗留去向）+ **外部单据关联表**（工单/需求单，模板占位——接入外部系统后启用，未接入时省略）+ 分期依据；范围边界含「不改哪里」负面清单。
- CURRENT：任务级状态 + **阶段位置表**（唯一活状态）。
- demand / design / plan 总体件；一行 INDEX；任务类型不限定（交付型均可用）；**前置调研保持独立任务、引用承接**（调研不一定会做，不绑定系列生命周期）。
- 总体把控四账只在根维护：范围（含不改哪里）、分期依据、外部单据关联、遗留去向——阶段目录不另立全局叙事。

**子阶段目录 = 交付单元**：

- 命名 `phase-{序号}-{英文短描述}/`；多阶段同一单据**省略单号段**（单号在系列层），仅该阶段绑定独立单据时插入；工作线目录（生命周期不同的寄生线）不套序号；封箱产物归任务内归档目录。
- 内含：阶段卡（静态 README：范围 / 验收 / 出口三件 / 单据关联）+ 该期 plan / review / verify-issues / process-log + 会话交接件。
- **不立 CURRENT、不设 status frontmatter**——活状态单一真源在根 CURRENT 阶段位置表；继续干活只写根 CURRENT（机检、看板、冷启动锚点不变）。
- 阶段并行判据（系列容器的核心收益就是多阶段并行）：**两禁一查**——禁① 阶段间有前置依赖（产物接口未冻结就开工 = 返工）；禁② 同文件冲突面大（两阶段改同一批文件，合并死锁/得不偿失）；一查 = 依赖只锁具体子件时按子件拆先行批（依赖重的子件后置串行、轻基建子件并行先行），位置表行内记依赖与并行批注记。
- 代码工作区：默认同根 worktree（跨阶段连续）；并行阶段需同仓不同分支时按阶段开独立 worktree（feature 分支名含单号天然区分）；着陆卡（\*.code-workspace）归阶段目录、随阶段生成。

**跨迭代**：不拆目录——任务根 frontmatter 按掉落改标机制随迭代归属更新（`sprint-log` 记轨迹，见 [WORKFLOW §2.7](../../../WORKFLOW.md)）；各阶段迭代归属记阶段位置表行。

## 三、分阶段决策流程（plan 编写期；不预设于立项）

立项时只登记单据关联；编写需求计划时跑**五轴检查**，缝 ≥2 即出拆分建议进讨论（操作者也可主动提出），**与操作者讨论怎么拆分合理后定**——信号是讨论辅助不是门禁：

| 检查轴 | 看什么 |
| ------ | ------ |
| 改动面分层 | 子项能否按仓库 / 技术域正交分组？层间是互为前置（单向消费、无正交缝）还是可独立推进？ |
| 依赖时点 | 有无外部输入（能力缺失 / 接口未定 / 设计稿未到位）造成「可先行 / 须后置」分层？期中是否无外部等待？ |
| 发布通道 | 各子项群的发布通道是否同质（统一集成分支整包 vs 多通道 MR / 发版 / 联调）？ |
| 验收口径 | 是否存在一个必须贯穿全部的回归矩阵 / 契约？还是各子项群有独立验收面？ |
| 规模信号 | 子任务数、跨仓数、预估迭代窗——超出单 plan 舒适区即加分 |

补充判读：后期改动预期会高频回落前期产物（施工方向「后改前」）、回滚粒度要求整包、验证环境重资产需跨阶段摊薄——这三类信号倾向单容器少切缝（阶段间强耦合，确认点可合并）；反之松耦合各阶段独立确认收口。单据是输入不是约束：单张工单可拆多阶段、多张工单可融一个阶段。plan 期产出的是**切缝草案**，终局切法允许随执行演化（阶段位置表动态承接）。

## 四、阶段出口门禁（阶段收口 = 三件同落）

1. **阶段确认**：操作者确认该阶段达成（允许操作者裁决合并确认点——强耦合系列合并为统一验收是合法形态）。
2. **单据闭环**：该阶段关联单据的提测 / 发布 / 回退闭环（单据系列 = 同一单据的分轮提测）——**提前发布是阶段出口的一等路径**，不是需要豁免的异常；出口后的回改走已发布版本的修复版本轨道。
3. **阶段封箱**：该阶段的补充叙事 / 产物收口归档，主文件留 digest + 指针。

## 五、边界（关联 ≠ 合并）

- 单据-任务交叉关联（多对多、网状）是常态：默认**独立任务 + 相互引用**（单据关联表承载），不强行合并进一个容器目录——合并仅在操作者明确要求时发生。
- 需求目标不同：引用而不并入。系列已真收官后的后续需求：开新任务引用原系列。

## 六、阶段位置表口径（CURRENT 内）

| 阶段 | sprint-version | 状态 | 单据关联 | 出口三件 |
| ---- | -------------- | ---- | -------- | -------- |

- 行独立记录、无顺序语义；出口三件列逐件记状态（确认 / 单据闭环 / 封箱）；收口后行更新、INDEX 摘要同步一句话。
- 系列地图 = 总目录 README 必备节（分期清单 + 指针 + 遗留去向），是「阶段位置表」的静态对照面。

## 七、与其他机制的关系

- **feat-plan-research 配对**：其复杂度画像判大需求时提示配对加载本 skill（plan 期五轴检查与拆分建议步）；非 feat 交付型独立命中。
- **subAgent 分治**：阶段内部执行手段，照常可用（并发纪律按 WORKFLOW 既有约定）。
- **阶段封箱**：与产物流分线 / 阶段封箱既有实践同族，本 skill 出口三件强制其随阶段确认执行。
- 系列目录仍是标准任务目录：立项登记、INDEX、机检、收尾门禁全部照常——本 skill 只加内层结构，不改外层任务规则。
