# AGENTS.md 章节编写规范

各章节的内容要求和编写原则。按需取舍——不是每个项目都需要所有章节。根据项目类型（前端/后端/全栈/库/CLI 工具）选择合适的章节组合。

## 通用原则

1. **只写可操作的规则**：每条内容必须能直接指导 Agent 的编码决策
2. **用代码示例而非纯文字**：展示"错误写法 → 正确写法"的对比
3. **不写 Agent 不负责操作的信息**：CI/CD 配置、发布流程、构建基础设施细节
4. **不写通过读代码就能学到的信息**：具体函数的实现细节、配置项的完整列表
5. **每条规则说明原因或后果**：让 Agent 理解"为什么"而不仅是"做什么"

### 篇幅与密度

每个章节应有行数上限，超过时触发精简：

| 章节 | 建议行数上限 | 说明 |
|------|-------------|------|
| 标题 | 2 | 项目名 + 技术栈一句话 |
| 环境与命令 | 10 | 版本、命令、端口 |
| 验证 | 8 | 改完代码后的验证步骤 |
| 核心架构 | 20 | 分层、入口、目录职责 |
| 关键编码约定 | 40 | 最重要的章节，用 ✅/❌ 对比 |
| 代码风格 | 10 | Linter、格式、import 约定 |
| 工程惯例 | 15 | 文件放置、请求方式、组件使用 |
| 约束和禁止 | 15 | 禁止行为列表 |
| 验证清单 | 10 | 变更检查项 |

- 用表格而非列表呈现映射关系（如知识库的域-文档表）
- 整体超出 200 行时优先删减「Agent 不遵守也不会怎样」的规则

### 针对不同语言/框架的适配

章节的名称和内容模板会因技术栈而异，以下规范提供的是**结构和原则**，具体措辞应根据项目实际情况调整。例如：

- 前端项目可能有"样式约定"章节，后端项目可能没有
- 使用依赖注入的后端项目可能有"服务注册"章节，前端项目可能没有
- 有国际化的项目需要"i18n"章节，纯内部服务可能不需要

## 标题

```markdown
# AGENTS.md — {项目名}
{一句话技术栈描述}。{语言} {版本}，{框架/工具}。
```

简洁明了，让 Agent 第一眼就知道项目的技术栈。

示例：

```markdown
# AGENTS.md — user-service
Go 微服务，用户中心。Go 1.22，Gin 框架，PostgreSQL。

# AGENTS.md — admin-homepage
Vue 2 单页应用，管理后台首页。Vue CLI 5 构建，Node 20。

# AGENTS.md — data-pipeline
Python 数据管道，ETL 处理。Python 3.11，Airflow 调度。
```

## 环境与命令

**内容**：

- 运行时版本（语言版本、Node/Python/Go/Java 版本等）
- 包管理器及锁定文件约定
- 本地开发启动命令、端口、入口
- lint/format 命令
- 测试命令
- 其他开发时需要的命令（数据库迁移、mock 服务、代码生成等）

**不包含**：

- build/publish 命令的详细说明（Agent 不负责构建发布）
- CI 环境变量说明
- 构建产物的部署地址

**模板**：

```markdown
## 环境与命令

- {语言} `{版本}`（见 `{版本文件}`）。用 `{包管理器} install`，禁止混用其他包管理器。
- 本地开发：`{启动命令}`。端口 `{port}`，入口 `{URL 或说明}`。
- `npm run lint`：{linter 说明}。
- {测试说明：有无测试、测试框架、测试命令}
```

## 验证

**内容**：

- **优先局部验证**：针对改动文件跑 lint/stylelint（单文件、快），而非每次全量校验整项目
- 区分两类检查，在验证章节中分别说明：
  - **可局部化**（lint、stylelint、format 等）：给出针对单文件的命令（如 `npx eslint <file> --fix`）
  - **不可局部化**（tsc/vue-tsc 等需全量上下文的类型检查）：改动后不强求执行，由 CI / pre-commit 兜底
- pre-commit 自动兜底的说明（如 husky + lint-staged 只校验暂存文件）

**模板**：

```markdown
### 验证

优先局部验证，针对改动文件跑 lint/stylelint（加 `--fix` 自动修复）：
- {语言} 单文件：`{局部 lint 命令} {文件路径}`

类型检查需全量上下文、无法局部跑，改动后暂不做，由 CI 统一兜底。
提交时 {pre-commit 工具} 自动校验暂存文件。
```

## 核心架构

**内容**：

- 技术栈版本和分层结构
- 入口文件/模块及其关系（哪些需要同步检查）
- 关键目录的职责
- 核心设计模式（状态管理、依赖注入、消息队列等）

**不包含**：

- 入口文件的详细实现描述
- 中间件/拦截器的具体逻辑
- 构建插件的工作原理

**模板**：

```markdown
## 核心架构

- **{技术栈}**。{分层描述}。
- {N} 个入口模块：`{路径1}`（{说明}）、`{路径2}`（{说明}）。涉及入口需同时检查 {相关模块}。
- `{目录}`：{职责}。
- `{目录}`：{职责}，新增前先检查是否可复用。
```

## 关键编码约定

**这是最重要的章节**。记录项目中容易被忽略但写错后影响大的编码约定。

**编写原则**：

- 每条约定必须说明"Agent 会怎么写错"和"正确写法"
- 用 ✅/❌ 对比展示
- 约定来源于代码探索，不是凭空设想

**代码示例格式**（必须遵循）：

```markdown
- **{约定名称}**：Agent 会用 {错误方式}，正确做法是 {正确方式}。原因：{为什么}

  ❌ 错误：{简短说明}
  {错误代码}

  ✅ 正确：{简短说明}
  {正确代码}
```

**常见约定类型**（按项目实际情况取舍）：

- 用户通知/消息方式
- API 数据转换（布尔值、枚举、时间等）
- 跨模块通信方式
- 状态管理的命名空间和访问规则
- 自动注册的模块（不需要手动 import 的）
- 环境判断方式
- 外部依赖/SDK 的版本管理和初始化
- 功能开关的来源和使用方式
- 日志和错误处理

**模板**：

````markdown
## 关键编码约定

- **{约定名称}**：用 `{正确方式}`，不要用 `{错误方式}`。原因：{为什么}

  ❌ 错误：{简短说明}
  ```

  {错误代码}

  ```

  ✅ 正确：{简短说明}
  ```

  {正确代码}

  ```
````

## 代码风格

**内容**：

- Linter/Formatter 配置来源
- 关键规则覆盖
- 格式约定（缩进、引号、分号等）
- 路径别名或 import 约定

**模板**：

```markdown
## 代码风格

- **{Linter}**: 继承 `{配置路径}`，{关键规则说明}。
- {语言} 文件：{缩进} 空格缩进、{引号类型}引号、{分号/无分号}、{路径/import 约定}。
```

## 工程惯例

**内容**：

- 文件/模块放置规则
- 网络请求方式（禁止自建客户端实例等）
- 外部依赖加载模式
- UI 组件库使用（前端项目）
- 服务注册方式（后端项目）
- 埋点/监控维护

**模板**：

```markdown
## 工程惯例

- {文件放置规则}。
- **网络请求**：用 `{请求工具/函数}`（→ `{目标服务}`）。禁止自建客户端实例。
- **{外部依赖}**：沿用 `{模式描述}`。
- **{组件/服务}**：{使用规则}。
```

## 样式约定（前端项目适用）

**内容**：

- CSS 类名前缀规则
- CSS 预处理器的使用规则（嵌套禁止等）
- 全局样式存放位置
- 主题/设计系统的使用方式

**模板**：

```markdown
## 样式约定

- 类名前缀：{前缀规则}，kebab-case。
- 全局样式只放在 `{目录}` 下；模块样式就近放。
- **{CSS 规则}**：{具体要求}。
- `{工具/loader}` 自动注入 `{全局样式/变量}`，可直接使用。
```

## 数据库约定（后端项目适用）

**内容**：

- ORM 使用方式和查询构建约定
- 数据库迁移规则和命令
- 事务管理模式
- 连接/会话管理

**模板**：

```markdown
## 数据库约定

- **ORM**：使用 `{ORM 名称}`，{用法说明}。新增模型放在 `{目录}`。
- **迁移**：`{迁移命令}`。{迁移文件命名规则}。
- **事务**：{事务管理模式}。{事务应在哪个层级开启}。
- **连接**：{连接获取方式}，{是否自动释放}。
```

## API 设计约定（后端项目适用）

**内容**：

- API 风格和路由定义规范
- 请求/响应格式约定
- 错误码体系
- 分页、排序、过滤参数规范

**模板**：

```markdown
## API 设计约定

- **风格**：{RESTful / RPC / GraphQL}。路由定义在 `{目录}`。
- **响应格式**：`{标准响应结构}`。成功判断条件：`{条件}`。
- **错误码**：`{错误码定义位置}`。新增错误码规则：{规则}。
- **分页**：参数格式 `{参数}`，响应格式 `{响应}`。
```

## 服务注册与依赖注入（使用 DI 框架的项目适用）

**内容**：

- DI 框架的使用方式
- 服务生命周期（单例、作用域、瞬态）
- 服务注册位置和方式

**模板**：

```markdown
## 服务注册与依赖注入

- **DI 框架**：使用 `{框架名称}`，{基本用法}。
- **注册位置**：服务在 `{目录/文件}` 中注册。
- **生命周期**：{单例/作用域/瞬态 的使用场景}。
- **新增服务**：{注册步骤}。
```

## i18n（有国际化的项目适用）

**内容**：

- 语言文件目录结构
- 旧文件和新文件的关系
- key 命名规范
- 不同上下文中的调用方式（组件 vs 工具函数 vs 模板 vs 服务层）
- 参数化文案写法
- 新增文案的同步流程

**模板**：

```markdown
## i18n

使用 `{i18n 库}`，所有用户可见文案必须走 i18n，不要硬编码。

- **语言文件**：`{目录路径}`，按模块分文件（`{模块列表}`）。
- **key 命名**：{命名规范}。
- **组件/视图内使用**：`{调用方式}`；工具函数/服务层中：`{调用方式}`。
- **参数化文案**：占位符用 `{格式}`，传参方式：`{方式}`。
- **新增文案流程**：在 `{文件路径}` 中同时添加相同 key。{扩展规则}。
```

## 约束和禁止

**内容**：

- 禁止的重构行为
- 禁止修改的文件/目录
- 禁止引入的依赖
- 禁止的代码模式

**模板**：

```markdown
## 约束和禁止

- 不要用大范围重构掩盖小需求。
- 不要改动无关模块或无关依赖版本。
- 不要直接编辑 `{自动生成目录}` 的产物。
- 不要提交临时文件或本地环境文件。
- 不要用 `git reset --hard` 回滚其他任务的改动。
- **{约束}**：{描述}。验证：`{shell 命令}` 应返回 {预期结果}。
```

## 验证清单

**内容**：

- 不同类型变更需要检查的项目
- 入口模块同步检查规则
- 全链路变更的检查项
- 外部依赖更新的验证
- 交付前最低验证标准

**模板**：

```markdown
## 验证清单

- 涉及入口模块：同时检查 {模块列表}。
- 涉及 {特定功能}：检查 {全链路文件列表}。
- 涉及外部依赖：验证 {版本/资源检查}。
- 交付前至少跑一种验证：`{命令1}`、`{命令2}` 或 `{命令3}`。
```

## 知识库

**内容**：

- 知识库目录位置
- 业务域到文档的映射表
- 知识库管理工具的使用指引

**不包含**：

- 知识库工具的详细命令说明（工具自身已有）
- 文档格式规范（工具自身已有）

**模板**：

```markdown
## 知识库

业务知识文档存放在 `notes/` 下。处理不熟悉的业务逻辑时，应先查阅对应文档。

| 业务域 | 文档 |
|--------|------|
| {业务域1} | `{文件名}` |
| {业务域2} | `{文件名}` |

知识库通过 `{工具名}` 管理，详见 `{命令列表}`。
```
