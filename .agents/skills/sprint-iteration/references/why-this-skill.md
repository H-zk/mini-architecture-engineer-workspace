# 为什么有 sprint-iteration（存在原因）

> 回答两个问题：**为什么要有迭代**、**迭代边界为什么需要一个 skill** 承载而不是散在 WORKFLOW 与回顾文档里的几条规则。改动本 skill 前、评估边界机制合理性前、与外部工作流对比前，先读本件。

## 为什么要有迭代

**迭代是敏捷开发的通行实践**——以固定节奏的时间盒组织交付、反馈与改进（Scrum 的 sprint 即此形态）。工作区与宿主业务都选择了这种方式，是选择而非必然：节奏由操作者每轮定参，可调可换。本 skill 机制层不与具体业务耦合——业务与方法论分离，含业务语义的细节留在业务知识层。

- **对齐宿主交付节奏**：宿主业务以迭代为单位运转，一次迭代承载多类任务；工作区用 `sprint-version` 把迭代立为显式概念（取值唯一真源 = WORKFLOW frontmatter），任务立项即标迭代号——归属清晰、并行任务有共同时间盒。
- **给治理一个周期性消化窗口**：迭代中业务为主、治理诉求默认攒批进 BACKLOG；边界批集中销账收口。没有周期窗口，治理债要么无限积压、要么随时打断业务。
- **给回顾与评估一个自然范围**：阶段回顾锚定「本迭代任务 + commit 范围」，评分账按迭代记账（ARCHITECTURE §4 迭代评分快照），相邻分层快照 diff 即版本差异分析——没有固定窗口，回顾范围要现圈、跨期质量不可比。
- **稳定 tag 的锚点序列**：每迭代一个 stable tag，构成跨周期信任根序列——外部学习 / 对比线可锚定「最近稳定 tag」取自洽真源（tag 过 [SKILL](../SKILL.md)「tag 七门禁」全绿才打——含销账零悬空与全部阶段推送齐）。
- **归档与任务生命周期的批次单元**：任务完成后留活跃区、迭代末统一归档——活跃区恒等于完整迭代范围，`grep sprint-version` 即得本迭代任务清单。
- **周期不写死**：每轮回顾定参（下个值 + 周期，操作者定）——迭代长度服务于业务与治理的平衡，不是机械日历。

有迭代，「边界怎么过」才成为问题——这是本 skill 的存在前提。

## 问题域：边界是治理的集中时点，且顺序敏感

工作区以迭代为节奏运转（`sprint-version` 唯一真源在 WORKFLOW frontmatter）。迭代主体是业务（需求 / CASE / 咨询 / 调研），治理诉求默认攒批进 BACKLOG；两端的边界批（结束批 / 开始批）集中消化治理债——销账、收口、清算、定参、准备。边界动作有三个特性，决定了它必须被显式编排：

1. **动作多且顺序敏感**：销账先于收口、收完才 tag、手册定稿先于确认、收尾推送先于打 tag——顺序颠倒即失效（tag 打在未收完的内容上即失真）。
2. **决策位密集**：遗留裁决门、确认闸门、销账逐项、exps 毕业确认、tag 授权都是操作者亲自下场的决策位。skill 的职责是把这些决策位摆到明处——AI 提议、操作者裁决。
3. **跨会话长流程**：结束批五阶段 × 十六步、开始批六步，中间穿插独立会话的 workspace-review 提交推送。进度必须落任务 CURRENT（留痕即进度），不能靠会话记忆。

## 不设防的失效形态（本 skill 防的是什么）

- **大尾批**：全部改动积到边界末尾一次性 commit——review 负担重、节奏差。对策 = 阶段出口门禁（每阶段收口即提交推送，不积尾）。
- **销账悬空**：裁决了但未归位的事项泄漏到 tag 后，治理债隐身。对策 = 销账四选一归位 + 零悬空完成判据。
- **tag 失真**：稳定 tag 是外部学习线的取真源锚（锚定「最近稳定 tag」），打在未收完 / 未推送的内容上即污染锚点。对策 = 七门禁 + tag 打在全部阶段推送之后。
- **状态靠猜**：迭代处于什么状态若靠记忆或会话上下文判断，换会话即失真。对策 = 判态三问 + 物证取法（tag / 手册头部当前态 / 回顾任务立项）——状态由物证推断、不另存字段，存出来的状态快照必过期。
- **口径失守**：汇总手册的业务能力分析若以任务活动量充当能力证据，即偏离能力资产口径。对策 = 生成时判据（固定指标清单逐层填 + 层间口径不互推，呈报前自检）。

## 设计取舍（为什么是现在这个形态）

- **三态而非两态**：边界按归属与物证锚、不按日期——回顾打 tag 与开始新迭代可同日紧邻，时间分段表达不了「结束与开始紧邻」的合法时序。首迭代冷启动无 tag——以首次定参（`sprint-version` 首次写入）为开始锚，状态机不依赖历史 tag 存在（新仓首次跑即此形态）。
- **单一真源 + 摘要指针**：WORKFLOW §2.7 只留元定义，执行细节全在本 skill；retrospectives README 管回顾本体（开放式深度分析，不固化成流程），本 skill 管边界怎么过——两文档分工防复写。
- **系列任务模式承载结束批**：结束批改动面大，按阶段分批提交推送（销账 / 清扫 / 归档 / 产物 / tag 五段）；review 需独立会话，阶段间以任务 CURRENT 续接，每阶段收口由 AI 交付接续提示词。
- **治理正向且健康（position 不变原则）**：边界批做多少治理不是问题，治理实效才是判据——skill 不设治理配额，只设节奏单元与门禁；迭代中治理诉求默认攒批，当期动 = 操作者显式裁决。
- **能自律不机检、再犯即升级**：口径类判据先落在生成时自检（上下文工程层）；同族错误 ≥2 实证即走 BACKLOG 通道升级为 workspace-check 机检分区（编排工程层）。

## 边界（本 skill 不做什么）

- 不承载回顾本体方法——怎么深度分析在 [retrospectives README](../../../../retrospectives/README.md) 的七层清算层表。
- 不约束迭代中的业务任务执行——各执行流 skill 的职责。
- 不维护迭代规划——需求规划归宿主业务方的任务系统【模板占位：如你的工单/项目管理系统】，工作区只记做了什么 + 做得怎样。
