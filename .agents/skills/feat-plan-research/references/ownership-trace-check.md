# 归属判断全链路核实（UI/字段属于什么业务，五环逐环锚定）

> 适用 = plan 期判断某 UI 元素/字段「属于什么业务、该归哪层」、跨端跨仓一致性核对、以及**照存量模板复刻任何「读状态/开关」的点**。前置判据：前端组件名/字段名是**线索不是结论**——技术债导致同名异义/异名同义，只看前端会误判。

## 五环全链路（每环给 file:line）

1. **后台配置入口**：管理员配的字段叫什么、上传分类是什么（如 `{type:'logoImage'}`）；
2. **前端映射**：后台字段如何映射成提交参数；
3. **后端 BO/落库**：后端注释、写入哪张表哪个字段（**注释常自爆真相**，如「水印图片URL」写在 `logoImage` 字段上）；
4. **下发字段**：接口下发的是 `pageSetting.logoImage` 还是 `shopConfig.watermark*`；
5. **前端渲染**：最终由哪个组件、以什么形态渲染（单张定位 logo vs 平铺 watermark）。

**判读**：链路一致 = 同一业务；链路在某环换名（后台叫水印、落库叫 logo）= 命名技术债——**按落库/渲染的真实归属归类，把命名混用记为技术债**，不把两个名字当两类业务。真相在**落库字段 + 渲染组件**（数据最终流向哪、由谁渲染）。

## 照模板复刻状态字段的语义溯源（三步）

模板抄的是形状，字段抄的是语义——后者必须独立核实：

1. `git log -S <字段>` 溯引入提交看当时用途（判例：模板里复用的 `status` 字段实为早年独立功能死键，同名前缀 ≠ 同体系）；
2. 全仓枚举消费链——**消费点仅模板自身 = 危险信号**（字段是死键复活）；
3. 对照本需求的开关体系（正确开关常在另一接口）。
