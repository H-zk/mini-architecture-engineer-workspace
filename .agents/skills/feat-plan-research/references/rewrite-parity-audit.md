# 重做型功能对照审计（旧版清单反向梳理 + 代码实况分级裁决）

> 适用 = 重做 / 重构 / 复刻 / 声明「1:1 对齐旧版」的 feat 任务，**写 plan 与点验/收口前读**。判别：任务记录写「对齐旧版」只是**编码者的自检声明**——功能是否真没丢，只有旧版代码逐项对照才算数；操作者说「改动比想象复杂」「会不会丢功能」即触发。

## 五步法

1. **旧版功能清单反向梳理**：以旧版分支代码逐文件提取「用户看到 + 用户可做」。前置 = 核实基线等价（如 master 与开发分支精确路径零 diff 才可互当真源）。产出**双版本**：
   - 技术版（`file:line` 锚点 + 开关英文名 + 条件显隐）——点验期望底稿与对账基准；
   - 纯产品版（业务语言、条件统一「（仅…）」表述、零代码痕迹）——产品确认与评注。
   两版互相引用，不做混合版（受众不同）。
2. **差异审计以新版代码实况为准**：读 worktree 当前态（含未提交修复），不引用任务记录自检结论；主壳与核心组件精读，弹窗族可 subAgent 逐对核对（给子代理旧版功能面清单作对照基准）。
3. **四级分类**（裁决友好）：A 旧有新无疑似缺失（无任何裁决依据覆盖）/ B 行为变更（与旧版实际行为不同，多为修旧缺陷方向）/ C 已裁决变更（逐项在码核实）/ D 增强。**「看似差异实为等价」单独成节防误报**（如确认文案拼接口径、双壳行为差异被正确保留）。
4. **操作者逐类裁决**：A 类逐项定（产品要求不改 / 修复 / 接受），B 类定调知悉或回改。两条守则：**旧有功能点在新版至少要有替代**；**借新版修问题时状态契约须与后端/产品语义对得上**。
5. **修复与复核**：A 类修复后审计文档标注处置结果；修复项进点验清单。

## 边界

- 审计对象是**功能面**（展示/交互/入口），不替代动线测试与开关组合回归。
- 旧版清单一份产出三用：点验期望底稿、产品确认件、差异审计基准。
- 别把结构耦合当缺陷根因——「要不要拆结构」是独立决策，依据是语义与回归成本，不是缺陷频率。
- 审计同时反哺调研真源：行号锚点在代码不变时长期有效，调研结论却可能被后续阅读纠正——审计差异即是调研修正源。
- 工具选型：符号图谱类对模板层展示提取价值低，人读 + subAgent 逐对对照更准。
- 同期双端行为对照（空间轴·跨端型）见 [pc-mobile-alignment-audit.md](./pc-mobile-alignment-audit.md)。

## 检查清单

- [ ] 旧版基线等价核实了吗（零 diff 证明或显式声明差异）？
- [ ] 清单出了双版本（技术版 + 产品版）吗？
- [ ] 差异审计读的是新版代码实况，不是任务记录自检声明？
- [ ] 四级分类 + 等价防误报节齐了吗，A 类逐项过操作者裁决？
