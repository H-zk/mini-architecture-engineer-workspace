# 代码评审执行纪律

> 适用 = 对 development worktree 代码变更的一切评审时刻（AI 自审修复轮、操作者终审打磨、验证期复核）。与 review.md 分工：review.md 管产物协议（审成什么样），本件管执行纪律（怎么审）。技法主体吸收自 tw93/waza check skill（MIT）。

## 评审前预检（Worktree 安全）

- 先 `git status --short --branch -uall` 读工作区现状；modified / staged / untracked 文件视为作者的工作，只读入评审面，不移动、不清理、不 stash、不「帮着挪去临时目录」。
- 评审过程禁默认执行 `git switch` / `git checkout` / `git reset --hard` / `git clean` / `git stash`（各变体同）；确需切分支或清理 → 停下，向操作者请求该精确操作的授权。
- 评审后有 commit/push 跟进动作的，动作前先记 `git rev-parse HEAD` 并复查——HEAD 漂移或出现未知提交即停并报告，不自行 rebase 补推。

## 评审技法六件套

1. **Sign-off 固定账本**：评审结论开头给状态行（现在处于什么态 + hash / 阻塞项），末尾给账本——scope 对齐态（on target / drift）、硬停项、兄弟扫描结果、测试情况、验证声明来源。账本让人不读全文也能对账裁决。
2. **兄弟扫描（sibling sweep，两问）**：diff 修复某类问题的一例时，全仓 grep 同型位点逐个确认其余实例已处理或本就不存在（**横向问：同款还有没有**）；修复新增或改变交互行为时，另扫它所替代、相邻的旧展示/旧入口是否同步收敛（**纵向问：新旧叠加有没有**——补新入口不收旧入口、改一处展示漏相邻位都是漏扫）；同风险未扫到 = 硬停级发现，低风险 = 提示级。
3. **历史敏感检查（history-sensitive）**：删除或反转既有保护性逻辑前，`git log -S` 考据该逻辑的引入动机；「刻意设计的不对称」被反转须有显式依据（工单 / 决策注释）留痕，否则按疑似无意破坏上报。
4. **测试面保真两问**：① 测试改动是否「在未修代码上会失败」——不会失败的测试改动是追认不是覆盖；② 断言路径是否生产真实路径——mock 自说自话不算。
5. **空转绿判据（hollow green）**：验证器在断言前挂掉、可选依赖缺失的 bootstrap 噪音、工具装配失败 = 「未跑成」，不是「通过」；反向同理——没跑到真实路径的绿不算绿（跳过的用例打印 OK、早退使空输出断言通过）。
6. **结构性不可测的报告纪律**：测试缺口若属基建 seam 缺失（如测试器无某文件类型 transform 导致页内组件不可测），按架构级缺陷报告并给下沉建议（如把逻辑抽到可测纯函数模块）；不强行造假 seam，不因「测不了」静默略过。

## 品味线（过度设计与组件选型维度）

- 每个新抽象 / 状态机 / 配置层过「删除测试」：删掉它需求仍成立 → 报过度设计嫌疑（提示级；有明确演进预期且 plan 已认可的计划项除外）。
- 简单表单 / 线性流程不上状态机：两态以下用局部状态 + 条件分支；多态且存在无序流转才值得状态机化。
- 修复粒度与问题粒度对齐：能就地局部修的不引入模式、不加层（「简易处理」取向）。
- 组件 / 依赖选型从最简够用起：原生能力 > 既有组件库 > 新引入依赖；新依赖出现必须在报告里给理由与被替代方案。

## 发现质量门槛（四问 + 三证据）

- 写进报告前四问：能引 file:line？能述**触发输入**（什么操作 / 参数 / 数据形态 / 状态会触发）？上下游已读非孤立看？严重度可辩护（资深评审会不会在这个级别提）？——任何一问「否」就降级为提示或丢弃。
- 高严重度发现须三证据：确切位置 + 具体触发 + 为何既有防护（校验 / 类型 / 上游 catch / 框架默认）不挡；三缺一降级。「某条件下可能会坏」不是高严重度。
- 干净评审合法：零发现且已声明审查面 = 合法完成；不造低置信噪声填充报告。
- 新增 catch 禁完全静默（可观测性缺陷，提示级）：容错 catch（缓存读写 / 可选依赖 / 上报旁路 / 非关键请求）写 `catch {}` 或 `catch { // 忽略 }` 即报「降级不可观测」——凡 catch 至少一条 warn 级日志，格式 `[模块前缀] 动作 failed` + err 对象（前缀便于过滤、err 保留堆栈；项目有统一 logger 优先用，不为一条日志引入依赖），降级返回值照常给，请求类 `.catch(() => {})` 同样适用。边界三条：既有静默 catch 不顺手改（只约束新增，防 diff 虚胖）；重试内层已由外层统一告警时可不打，但整条链路至少一处留痕；review 自检 grep 本次 diff 的 `} catch {` / `catch {}` / `// ignore` 逐个确认已留痕。

## 证据边界（声明三分类 + 深挖不豁免）

- 评审产物的验证声明按三分类标注：**本会话实跑**（命令输出在场）/ **reading-the-code 推断**（读码推理，未执行）/ **环境限制跳过**（无授权或工具不可达）。写「已验证」必须属第一类。
- 仓内不可验证 ≠ 深挖豁免：对不可验证面（后端契约、外部系统行为、跨服务匹配语义）继续推演**具体失败场景**，标注意图与验证路径（例：「复制展示 ID → 粘贴搜索 → 应命中」，交验证期 E2E 闭环）——不许停在「不可验证」四个字上把风险吞掉。
