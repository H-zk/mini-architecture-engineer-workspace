# 跨端同功能对齐核查（对比读码 + 差异三分出路）

> 适用 = 跨端同功能需求：一端已有实现（如 PC），另一端新做或声称「对齐 PC」；交付自检与验证期需要回答「两端行为到底一致到什么程度」。与重做型（新旧版本·时间轴）对照见 [rewrite-parity-audit.md](./rewrite-parity-audit.md)——判据族同源，场景互补。

## 为什么主流程相似 ≠ 行为一致

不做系统核查时，「对齐」停留在主流程截图相似——同名流程里的**分支差异**漏掉：拦截分支（通用拦截 vs 专属引导）、实时同步（他端操作即时反映）、详情跳转定向、footer 能力集（导出/分享）、默认值。UI 对比看不出来，**对比读码才查得出**。

## 方法

1. **对比对象 = PC 同名流程的代码路径，不是 UI**：沿两端同名入口（hook/composable）逐分支核对——前置校验/拦截分支、引导文案、事件（socket）监听、成功后定向、footer 按钮集。
2. **每个差异登记一行**（问题/根因/可达性），再按三类出路裁决：
   - **修复对齐**（行为差异属遗漏）→ 补丁级修，对齐 PC 语义；
   - **产品决策**（能力是否提供是需求问题）→ 与产品确认，不擅自对齐（裁决「不提供」的，已写的实现代码删干净，不留半成品 prop/emit）；
   - **确认设计内**（端形态差异）→ 登记不处理。
3. **可达性评估**：差异只在极端操作可达（毫秒级连点双开弹层）且无数据错乱时，按轻微体验毛刺裁决接受度，不强求代码级互斥。
4. 核查时机：交付前自查一轮 + 验证期一轮（联调前）；发现即登记 verify-issues，不在 review.md 追加。

## 检查清单

- [ ] 两端同名流程是否逐分支对比过（拦截分支 / 引导文案 / socket 监听 / 成功定向 / footer 能力）？
- [ ] 每个差异是否登记并裁决出路（修复 / 产品决策 / 设计内）？
- [ ] 产品裁决「不提供」的能力，实现代码是否删干净？
- [ ] 极端场景才可达的差异是否评估过可达性与数据影响？
